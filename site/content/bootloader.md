A **bootloader** is a small program resident in a device's program storage that runs first at power-up, checks the application image for validity, and transfers execution to it when the image is good.<sup><a href="#ref-212" data-tip="Ep 212: An Interview with Trey German - Launchpad Laden Lodesman (August 18, 2014)" title="Ep 212: An Interview with Trey German - Launchpad Laden Lodesman (August 18, 2014)">[212]</a></sup> Its primary purpose is to allow the application firmware to be replaced in the field: updating requires a route for the running application to re-enter the bootloader, after which a replacement image arrives over whatever communication channel the product already has — a vehicle bus, USB, or a plain serial link.<sup><a href="#ref-212" data-tip="Ep 212: An Interview with Trey German - Launchpad Laden Lodesman (August 18, 2014)" title="Ep 212: An Interview with Trey German - Launchpad Laden Lodesman (August 18, 2014)">[212]</a></sup> The mechanism exists because the alternative is physical access: a microcontroller buried in a product cannot be removed, opened, and reprogrammed through its debug header when a defect is found.<sup><a href="#ref-212" data-tip="Ep 212: An Interview with Trey German - Launchpad Laden Lodesman (August 18, 2014)" title="Ep 212: An Interview with Trey German - Launchpad Laden Lodesman (August 18, 2014)">[212]</a></sup>

## Purpose and operation

Without a bootloader, loading code requires access to the debug pins and a hardware programmer, which is precisely the alternative the bootloader exists to avoid.<sup><a href="#ref-589" data-tip="Ep 589: Mute Button Discipline (May 15, 2022)" title="Ep 589: Mute Button Discipline (May 15, 2022)">[589]</a></sup> The bootloader therefore occupies a privileged position in a product's architecture: it is the component that must survive every update, and everything needed for recovery must live inside its protected region — placing the radio routines there, for example, is what allows a device with a completely broken application to be recovered wirelessly.<sup><a href="#ref-516" data-tip="Ep 516: Thermions Aren't A Thing (November 8, 2020)" title="Ep 516: Thermions Aren't A Thing (November 8, 2020)">[516]</a></sup>

A bootloader can decide what to do from its environment. One board's bootloader stays resident and waits for a command when it detects a connected host, and automatically boots the previously loaded user configuration when it finds only a power supply.<sup><a href="#ref-395" data-tip="Ep 395: An Interview with Luke Valenty (June 3, 2018)" title="Ep 395: An Interview with Luke Valenty (June 3, 2018)">[395]</a></sup> Keeping the bootloader in a separate serial flash preserves a recovery path, so a hard reset can always bring the device back up even after a user configuration has replaced it in the running device.<sup><a href="#ref-395" data-tip="Ep 395: An Interview with Luke Valenty (June 3, 2018)" title="Ep 395: An Interview with Luke Valenty (June 3, 2018)">[395]</a></sup> Booting the entire firmware from a removable card is a stronger variant of the same idea: a bad image is replaced by swapping the card rather than by recovering the device, eliminating the bricking risk.<sup><a href="#ref-325" data-tip="Ep 325: An Interview with David Kronstein (Tesla500) (November 30, 2016)" title="Ep 325: An Interview with David Kronstein (Tesla500) (November 30, 2016)">[325]</a></sup>

### Larger systems

On a system with memory management, the bootloader's task is to read the kernel image from storage into memory at some address and set the program counter to it, after which the kernel takes over.<sup><a href="#ref-515" data-tip="Ep 515: Embedded Linux with Jay Carlson (November 1, 2020)" title="Ep 515: Embedded Linux with Jay Carlson (November 1, 2020)">[515]</a></sup> Porting such a system to a new board requires a bootloader that knows how to load the kernel for that architecture before any of the kernel's hardware abstraction becomes useful.<sup><a href="#ref-378" data-tip="Ep 378: An Interview with Jason Kridner and Robert Nelson (February 4, 2018)" title="Ep 378: An Interview with Jason Kridner and Robert Nelson (February 4, 2018)">[378]</a></sup> Because the bootloader is part of the storage image rather than the kernel, supporting a variant board that needs a different bootloader means patching the disc image rather than booting the same card unmodified.<sup><a href="#ref-378" data-tip="Ep 378: An Interview with Jason Kridner and Robert Nelson (February 4, 2018)" title="Ep 378: An Interview with Jason Kridner and Robert Nelson (February 4, 2018)">[378]</a></sup>

## Design principles

The governing principle of bootloader design is simplicity: the bootloader should be kept as simple as it can possibly be, because every additional capability is another way for the one irrecoverable component to fail.<sup><a href="#ref-364" data-tip="Ep 364: The Endless Y2K (October 22, 2017)" title="Ep 364: The Endless Y2K (October 22, 2017)">[364]</a></sup> The standard to aim at is that nothing can go wrong with the bootloader once the product has shipped and that it remains compatible with every future release.<sup><a href="#ref-364" data-tip="Ep 364: The Endless Y2K (October 22, 2017)" title="Ep 364: The Endless Y2K (October 22, 2017)">[364]</a></sup>

On one instrument, that principle produced a bootloader containing only four things: code to read the memory card, the display routines, simple button reading for the key combination that triggers an update, and nothing else.<sup><a href="#ref-364" data-tip="Ep 364: The Endless Y2K (October 22, 2017)" title="Ep 364: The Endless Y2K (October 22, 2017)">[364]</a></sup> Even a well-scoped bootloader can need revision once — on that product, a display contrast fault caused by incorrectly set registers had to be fixed in the bootloader because the display code lived there.<sup><a href="#ref-364" data-tip="Ep 364: The Endless Y2K (October 22, 2017)" title="Ep 364: The Endless Y2K (October 22, 2017)">[364]</a></sup>

The reason simplicity matters is that changing the bootloader on a shipped product is the dangerous operation: it requires the vendor's development kit and an internal fine-pitch header, and a failed write bricks the unit outright.<sup><a href="#ref-364" data-tip="Ep 364: The Endless Y2K (October 22, 2017)" title="Ep 364: The Endless Y2K (October 22, 2017)">[364]</a></sup> For the same reason, on Mike Harrison's production practice the bootloader is written first and then used as the means of loading code throughout development, so that by the time the product ships it has been exercised thousands of times and is known to be sound.<sup><a href="#ref-294" data-tip="Ep 294: Live from Serbia with Mike Harrison (April 13, 2016)" title="Ep 294: Live from Serbia with Mike Harrison (April 13, 2016)">[294]</a></sup> The reason to sequence it that way is that the bootloader is the one component that has to be beyond doubt, and writing it last leaves it the least tested part of the product.<sup><a href="#ref-294" data-tip="Ep 294: Live from Serbia with Mike Harrison (April 13, 2016)" title="Ep 294: Live from Serbia with Mike Harrison (April 13, 2016)">[294]</a></sup>

### Memory layout

Microcontrollers commonly provide a separate, segregated, and protected region of program memory for the bootloader, which is limited in size — on the order of a couple of kilobytes — and cannot simply be extended when more is wanted.<sup><a href="#ref-516" data-tip="Ep 516: Thermions Aren't A Thing (November 8, 2020)" title="Ep 516: Thermions Aren't A Thing (November 8, 2020)">[516]</a></sup> On parts with a vendor radio stack, that stack occupies a reserved block at the bottom of the address space while the bootloader sits at the very top, with both required to be protected memory.<sup><a href="#ref-516" data-tip="Ep 516: Thermions Aren't A Thing (November 8, 2020)" title="Ep 516: Thermions Aren't A Thing (November 8, 2020)">[516]</a></sup> The limited space shapes product features directly: one intended design in which stored data would be transferred wirelessly was abandoned because the storage access code would have had to live in the bootloader and there was no room for it.<sup><a href="#ref-690" data-tip="Ep 690: Clap on, clap off, lights flicker (March 11, 2025)" title="Ep 690: Clap on, clap off, lights flicker (March 11, 2025)">[690]</a></sup> At the extreme of cost, a ten-cent processor provides roughly nineteen hundred bytes of dedicated boot area alongside sixteen kilobytes of flash, and fitting a USB stack into that area makes the part programmable over USB with no external programmer.<sup><a href="#ref-637" data-tip="Ep 637: CH32V003...fun! with CNLohr (June 25, 2023)" title="Ep 637: CH32V003...fun! with CNLohr (June 25, 2023)">[637]</a></sup>

## Update mechanisms

A robust update scheme makes the transfer atomic. Placing the received image in an external flash before committing it achieves this: the bootloader looks for a complete image and does nothing if the transfer broke off partway, which matters because a wireless transfer can be interrupted at any point.<sup><a href="#ref-398" data-tip="Ep 398: An Interview with Felix Rusu (July 9, 2018)" title="Ep 398: An Interview with Felix Rusu (July 9, 2018)">[398]</a></sup> The sequence in that arrangement is that the running application receives the image into external storage and reboots, after which the bootloader detects a new image, erases the old application, writes the new one, and jumps to it.<sup><a href="#ref-398" data-tip="Ep 398: An Interview with Felix Rusu (July 9, 2018)" title="Ep 398: An Interview with Felix Rusu (July 9, 2018)">[398]</a></sup> A comparable design derived its bootloader from an existing open-source one, expanded the reserved bootloader region on a part chosen for having space, and taught the bootloader to boot from an external serial flash into which the application downloads a hex file that the bootloader parses directly.<sup><a href="#ref-250" data-tip="Ep 250: An Interview with Vic Aprea - Federated Firmware Functionalism (May 20, 2015)" title="Ep 250: An Interview with Vic Aprea - Federated Firmware Functionalism (May 20, 2015)">[250]</a></sup>

Compactness can dictate the protocol itself. One minimal loader avoids acknowledgements entirely by determining the baud rate from a preamble and relying on the sender to insert padding bytes calculated so that the flash write has completed before the next frame arrives, making the transfer a strictly one-way stream.<sup><a href="#ref-697" data-tip="Ep 697: LEDs Everywhere with Tim from Mitxela (July 8, 2025)" title="Ep 697: LEDs Everywhere with Tim from Mitxela (July 8, 2025)">[697]</a></sup> Because such a loader needs only a single wire, pairing it with an infrared receiver turns it into a wireless update path on a part with no radio at all.<sup><a href="#ref-697" data-tip="Ep 697: LEDs Everywhere with Tim from Mitxela (July 8, 2025)" title="Ep 697: LEDs Everywhere with Tim from Mitxela (July 8, 2025)">[697]</a></sup> Firmware update over USB likewise requires at least a bootloader resident on the microcontroller, which is part of why a plain serial interface is simpler for a product that only needs to move console data.<sup><a href="#ref-551" data-tip="Ep 551: Feed the Mouse (July 25, 2021)" title="Ep 551: Feed the Mouse (July 25, 2021)">[551]</a></sup> On contemporary modules, the standard circuit for entering bootloader mode uses a pair of cross-wired transistors driven from the serial adapter to assert the boot pin and then reset the part automatically.<sup><a href="#ref-702" data-tip="Ep 702: Test Point Accupuncture (September 14, 2025)" title="Ep 702: Test Point Accupuncture (September 14, 2025)">[702]</a></sup>

Implementing the loading interface in the device itself, rather than adding a dedicated programming chip, removed cost from one board design, making the finished product substantially cheaper for the buyer.<sup><a href="#ref-395" data-tip="Ep 395: An Interview with Luke Valenty (June 3, 2018)" title="Ep 395: An Interview with Luke Valenty (June 3, 2018)">[395]</a></sup>

## Manufacturing and provisioning

Microcontroller parts can be bought pre-programmed from the manufacturer against a minimum order of about a hundred and fifty pieces, adding roughly two days of setup and two days to the order lead time — worthwhile at volumes where programming thousands of leadless packages on the board would be impractical.<sup><a href="#ref-224" data-tip="Ep 224: Meracious Mike Manuduction (November 12, 2014)" title="Ep 224: Meracious Mike Manuduction (November 12, 2014)">[224]</a></sup> Loading only a bootloader at that stage is sufficient, since the application can then be written while the parts are in transit and blown down the serial bus in production.<sup><a href="#ref-224" data-tip="Ep 224: Meracious Mike Manuduction (November 12, 2014)" title="Ep 224: Meracious Mike Manuduction (November 12, 2014)">[224]</a></sup> Production programming can also be delegated cheaply by handing a subcontractor an inexpensive programmer with the code preloaded, reducing the operation to connecting it, pressing a button, and waiting for a green light.<sup><a href="#ref-224" data-tip="Ep 224: Meracious Mike Manuduction (November 12, 2014)" title="Ep 224: Meracious Mike Manuduction (November 12, 2014)">[224]</a></sup>

High-volume consumer production tends toward pre-programmed parts because there may be no room on the board for a programming header, which forces the firmware — or at least the bootloader — to be ready earlier than a low-volume product would require.<sup><a href="#ref-363" data-tip="Ep 363: An interview with Alvaro and Jen from the URE Podcast (October 15, 2017)" title="Ep 363: An interview with Alvaro and Jen from the URE Podcast (October 15, 2017)">[363]</a></sup> Even where every subsequent release arrives over the air, the device has to be programmed once physically, and that first programming step is the critical one.<sup><a href="#ref-544" data-tip="Ep 544: Standardizing Manufacturing with Pete Staples (June 1, 2021)" title="Ep 544: Standardizing Manufacturing with Pete Staples (June 1, 2021)">[544]</a></sup> Shipping a first-generation product before the software is finished means the only thing that can be loaded at the factory is the bootloader, with everything else arriving later.<sup><a href="#ref-256" data-tip="Ep 256: Is This A Show? (July 1, 2015)" title="Ep 256: Is This A Show? (July 1, 2015)">[256]</a></sup> The pattern of a factory-programmed bootloader loadable through an ordinary serial port, with no dedicated programmer, is what made early accessible microcontroller boards possible and remains the pattern used today.<sup><a href="#ref-570" data-tip="Ep 570: Keyzermas All The Way (December 19, 2021)" title="Ep 570: Keyzermas All The Way (December 19, 2021)">[570]</a></sup>

A proprietary bootloader can also be the commercial mechanism by which a module vendor protects its work, so designing that module into a product means buying the board or a separately sold pre-programmed part rather than the bare processor.<sup><a href="#ref-713" data-tip="Ep 713: Rubber Duck Incarnate (January 25, 2026)" title="Ep 713: Rubber Duck Incarnate (January 25, 2026)">[713]</a></sup> In one such case the restriction followed from a non-disclosure agreement covering the chip's security features, which is also what made a lockable variant offering encrypted firmware and a secure update process possible at all.<sup><a href="#ref-713" data-tip="Ep 713: Rubber Duck Incarnate (January 25, 2026)" title="Ep 713: Rubber Duck Incarnate (January 25, 2026)">[713]</a></sup>

## Security

A bootloader can be the mechanism by which software intellectual property is protected: an encrypted bootloader is programmed into the part at a secure facility with no network access, after which the programmed part is consigned to the assembly factory.<sup><a href="#ref-113" data-tip="Ep 113: An Interview with Scott Miller - Sudden SinoAmerican Synthesis (September 16, 2012)" title="Ep 113: An Interview with Scott Miller - Sudden SinoAmerican Synthesis (September 16, 2012)">[113]</a></sup> That arrangement also controls the supply chain, because a factory issued with a counted number of programmed parts cannot run an unauthorised extra production shift, and it allows subsequent images to be sent as encrypted files rather than delivered physically.<sup><a href="#ref-113" data-tip="Ep 113: An Interview with Scott Miller - Sudden SinoAmerican Synthesis (September 16, 2012)" title="Ep 113: An Interview with Scott Miller - Sudden SinoAmerican Synthesis (September 16, 2012)">[113]</a></sup>

### Roots of trust

A root of trust boots an otherwise untrusted system by verifying each stage in turn: an unchangeable first-stage bootloader in read-only memory validates and starts the next, which validates the one after, and the same component subsequently governs signing and firmware updates so a malicious image is rejected.<sup><a href="#ref-693" data-tip="Ep 693: Small Scale Electronics Manufacturing with Colin O'Flynn (May 13, 2025)" title="Ep 693: Small Scale Electronics Manufacturing with Colin O'Flynn (May 13, 2025)">[693]</a></sup> Such a root of trust is isolated by construction, with its only connection being to a service processor responsible for delivering update data to it securely.<sup><a href="#ref-590" data-tip="Ep 590: Finding Hardware Flaws with Laura Abbott (May 22, 2022)" title="Ep 590: Finding Hardware Flaws with Laura Abbott (May 22, 2022)">[590]</a></sup> Key material can be held in one-time-programmable antifuse memory, with hardware able to permanently disable reads or writes to part of the array or to disable access until the next reset; the intended pattern is that an early bootloader reads the key, uses it, wipes its own memory, and then locks the key away for the rest of the session.<sup><a href="#ref-687" data-tip="Ep 687: The RP2350 with the Raspberry Pi Team (January 28, 2025)" title="Ep 687: The RP2350 with the Raspberry Pi Team (January 28, 2025)">[687]</a></sup>

### Attacks and weaknesses

Encrypting the bootloader is not a checkbox: an implementation on real embedded hardware leaks through power consumption, because driving more lines high costs measurably more current than driving them low, and those differences can be measured and used to recover the key.<sup><a href="#ref-239" data-tip="Ep 239: An Interview with Colin O'Flynn - Aspirated Adamantine Attacks (March 3, 2015)" title="Ep 239: An Interview with Colin O'Flynn - Aspirated Adamantine Attacks (March 3, 2015)">[239]</a></sup> The relevant standard was defined without an attacker holding the device in mind, and the countermeasures are largely at the hardware level, such as balanced registers that set one line high whenever another goes low so no net switching is visible.<sup><a href="#ref-239" data-tip="Ep 239: An Interview with Colin O'Flynn - Aspirated Adamantine Attacks (March 3, 2015)" title="Ep 239: An Interview with Colin O'Flynn - Aspirated Adamantine Attacks (March 3, 2015)">[239]</a></sup>

A common structural weakness is that a failed check falls into an infinite loop rather than halting the processor, so an attacker who can skip past that loop finds the remaining code sitting there ready to run.<sup><a href="#ref-552" data-tip="Ep 552: Shouting at chips with Colin O'Flynn (August 1, 2021)" title="Ep 552: Shouting at chips with Colin O'Flynn (August 1, 2021)">[552]</a></sup> The three established ways of disrupting logic to defeat a secure boot process are voltage glitching, which perturbs the whole supply rail; laser fault injection, which reaches very small regions of logic because silicon is relatively transparent in the infrared; and electromagnetic injection through a small coil, which is localised but less precise than a laser.<sup><a href="#ref-687" data-tip="Ep 687: The RP2350 with the Raspberry Pi Team (January 28, 2025)" title="Ep 687: The RP2350 with the Raspberry Pi Team (January 28, 2025)">[687]</a></sup> In a public challenge against one such implementation, the practical breaks included faulting the signature check with a laser, injecting a fault into the USB bootloader by disturbing the supply, and extracting the one-time-programmable secret directly by imaging the die.<sup><a href="#ref-687" data-tip="Ep 687: The RP2350 with the Raspberry Pi Team (January 28, 2025)" title="Ep 687: The RP2350 with the Raspberry Pi Team (January 28, 2025)">[687]</a></sup> The recurring design failure in secure boot is disproportionate attention: enormous effort goes into resisting fault injection while a crafted flash image or a crafted packet arriving over the update interface opens the device without needing physical access at all.<sup><a href="#ref-687" data-tip="Ep 687: The RP2350 with the Raspberry Pi Team (January 28, 2025)" title="Ep 687: The RP2350 with the Raspberry Pi Team (January 28, 2025)">[687]</a></sup> Boot code kept in an ordinary serial flash alongside a server's processor is straightforward to modify, making it a far cheaper route for an attacker than fabricating custom hardware.<sup><a href="#ref-418" data-tip="Ep 418: An Interview with Josh Datko (December 2, 2018)" title="Ep 418: An Interview with Josh Datko (December 2, 2018)">[418]</a></sup>

## Implementation in practice

Writing a bootloader in house means deciding how to divide the program storage into regions that support robust image updates, and settling the versioning scheme and whether rollback to an earlier image is permitted at all.<sup><a href="#ref-590" data-tip="Ep 590: Finding Hardware Flaws with Laura Abbott (May 22, 2022)" title="Ep 590: Finding Hardware Flaws with Laura Abbott (May 22, 2022)">[590]</a></sup> Bootloader code is largely reusable across products, so a practitioner accumulates bootloader libraries in which the high-level update protocol is shared and only a platform-specific portion has to be adapted.<sup><a href="#ref-518" data-tip="Ep 518: Satellites and EVs with Joris Aerts (November 22, 2020)" title="Ep 518: Satellites and EVs with Joris Aerts (November 22, 2020)">[518]</a></sup> Silicon vendors increasingly supply the pieces, with storage-card and firmware-loading code already written, which removes the need to implement the bootloader from scratch.<sup><a href="#ref-364" data-tip="Ep 364: The Endless Y2K (October 22, 2017)" title="Ep 364: The Endless Y2K (October 22, 2017)">[364]</a></sup> The task also has a reputation that exceeds its difficulty: one bootloader that a team had been trying to hire out was written over a weekend once someone simply attempted it.<sup><a href="#ref-438" data-tip="Ep 438: An Interview with Bart Dring (April 14, 2019)" title="Ep 438: An Interview with Bart Dring (April 14, 2019)">[438]</a></sup>

## Failure modes

Omitting the bootloader from a shipped firmware image is unrecoverable: once such an image was loaded, the devices could not be reloaded at all.<sup><a href="#ref-215" data-tip="Ep 215: Wrong Hardware, Wrong Software - Fugacious Fan Funding (September 7, 2014)" title="Ep 215: Wrong Hardware, Wrong Software - Fugacious Fan Funding (September 7, 2014)">[215]</a></sup> Multiple processors in one product multiply the problem, since one must pass code to another and a power loss during that transfer is unrecoverable; good bootloaders can be designed for it, but it remains an argument for keeping the number of separately updatable firmware images down.<sup><a href="#ref-187" data-tip="Ep 187: An Interview with Elecia White - Wirewove Worshipping Wookieist? (March 3, 2014)" title="Ep 187: An Interview with Elecia White - Wirewove Worshipping Wookieist? (March 3, 2014)">[187]</a></sup>

A bootloader also interferes with debugging: a debugger that has no symbols for it loses track when execution enters it, and one project found its debug session only worked once the bootloader was removed.<sup><a href="#ref-383" data-tip="Ep 383: An Interview with Scott Shawcroft" title="Ep 383: An Interview with Scott Shawcroft">[383]</a></sup> The same effect appeared with a widely used open bootloader, where debugging failed until it was taken out, so anyone debugging on a system with one initialised should expect to do extra work.<sup><a href="#ref-509" data-tip="Ep 509: Cellular IoT with Jared Wolff (September 20, 2020)" title="Ep 509: Cellular IoT with Jared Wolff (September 20, 2020)">[509]</a></sup>
